# 下一批作品：项目方向与证据计划

整理日期：2026-09-22。

状态：本人确认 Agent、Jev / Laya 应用和 AI 社媒账号都仍在规划阶段。下面是建议范围与交付目标，没有对应实现或实测结果；尚未作为已完成项目加入作品列表。

## 1. 有权限边界的资料研究 Agent

建议从一个完整任务开始：读取指定的公开资料，回答研究问题，输出带引用的简报，经确认后保存到允许的草稿目录。

第一版只处理一个明确资料集和一类研究任务。文件系统、浏览器和外部服务的工具接入按真实需要添加。

| 工程方向    | 第一版要解决的问题                                           | 需要留下的证据                                           |
| ----------- | ------------------------------------------------------------ | -------------------------------------------------------- |
| RAG         | 找到相关片段，识别证据不足，保留可追溯引用                   | 固定文档版本、查询与相关片段标注、检索结果、引用核对样例 |
| Harness     | 运行任务、调用工具、记录中间状态；处理超时、重试、取消和预算 | 一次成功轨迹与一次失败恢复轨迹、状态图、工具输入输出     |
| Permissions | 限制可读目录和可写目录，区分读写与外部发送                   | 权限矩阵、允许/拒绝案例、审批事件记录                    |
| Evaluation  | 判断任务是否完成、引用是否可靠，以及策略修改是否有效         | 固定样本、基线、失败分类、逐条结果和回归报告             |

权限由工具执行层的确定性检查落实。检索文档里的指令和模型对风险的评分都不能直接扩大权限；写入、外发等操作的授权需要明确可核对。

第一份演示：给出问题 → 检索并核对来源 → 生成简报 → 预览保存动作 → 写入许可目录。再演示一次越界访问被拒绝、一次工具超时的恢复。

首轮可先设计约 20–30 条可人工核对的样例，覆盖有答案、无答案、来源冲突、恶意文档指令和工具失败。这是建议的起步规模，不是已有 benchmark。之后区分调试集和留出的评估集，并记录模型、配置、资料版本与实际调用成本。

## 2. Jev / Laya：对话与评论分流实验

### 模型定位

Jev 的发布方将其定位为从输入状态生成带概率的结构化判断；Laya 的作者模型卡也提供 typed-decision 接口。两者适合被评估为分类/路由模块，不能据此假设它们承担了完整的 OCR、长篇解释或开放式解题。

中文实验需要核对 Laya 的多语言 checkpoint 与输入长度限制。模型卡明确区分基础与特定任务微调版本，并提示置信度需要在目标数据上检验；不要把发布方的速度、校准或准确率直接写成自己的成果。

截至本次查阅的第一手资料：

- [TypeSafe：Introducing System One Models & Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev)
- [Jev 的 Cloudflare 模型文档](https://developers.cloudflare.com/ai/models/typesafe/jev/)
- [Laya 作者模型卡](https://huggingface.co/convaiinnovations/laya)
- [Laya 作者仓库](https://github.com/NandhaKishorM/laya)

### 建议先做：对话／评论分流台

输入一段短对话或评论，返回预定义的意图、表达倾向、是否需要人工处理，以及模型给出的概率；允许用户更正标签。分析对象是文本中可观察的表达，不把结果当成对人的心理状态诊断。

第一版人工导入可公开或获准使用的文本，展示批量分类、逐条复核和导出结果。与账号自动回复或自动处置先不绑定。

可考虑的标签：提问、反馈、投诉、闲聊；语气：积极、中性、负面、不明确。意图和语气可以使用独立字段，标签体系允许“不明确”和多重意图，不强迫歧义文本拥有唯一答案。

实验流程：

1. 先定义标签与人工标注规则，检查标注分歧。
2. 以简单规则和一个适当的分类基线作为参照；条件允许时加入通用 LLM。
3. 在同一批固定输入上比较 Jev 与匹配语言的 Laya 版本。
4. 分开记录冷启动、预热后推理、本地与 API 的端到端耗时；记录模型版本、设备、批量大小和网络条件。
5. 输出每类 precision / recall、macro-F1、混淆矩阵、延迟分布，以及概率与正确率的关系。单标签概率分类可以记录 Brier score 和校准图。
6. 若调节阈值、做温度校准或微调，在独立调试/验证集上完成；最后在留出的测试集上报告。

一个有说服力的成果：清楚说明模型在哪些文本上可靠、哪些边界样例会错，以及什么阈值下交给人工更合适。结果可以是一个模型不适合任务，前提是方法与记录可复查。

### 备选：试卷快速导览

如果选择试卷方向，建议先聚焦“读入已识别的题目，整理题型、预定义知识点和阅读优先级”。扫描试卷需要额外 OCR / 版面解析；第一版可以先支持干净文本。

Jev / Laya 可以作为结构化分类层的候选。长解释、步骤推导和复杂解题需要另外设计，不能由“支持结构化输出”推出相应能力。评估时将 OCR / 题目切分的错误与分类错误分别记录。

对话分流与试卷导览先选一个实现，避免同时引入两套数据和评价标准。

## 3. AI 社媒账号：持续创作与运营记录

先选一个平台、一个受众和一个栏目。建议将正在做的 Agent 或模型实验转成可演示的内容：一个失败案例、一段完整工作流、一次模型对比。Aodcast 也可以成为音频制作素材来源。

第一版流程：选题 → 查证来源 → 写脚本 → 生成或制作素材 → 剪辑 → 人工审核 → 人工发布。账号、平台和发布权限由本人确定；本规划不启动发布或消息发送。

建议先完成 3 条可以独立展示的内容，用来建立制作流程，而不是先承诺粉丝目标。保留原稿、最终作品、使用工具、本人修改部分和每条内容的实际制作时间。

如果有运营结果，记录截至日期、平台指标的口径、原始后台截图和观察区间。自然流量与付费推广分开记录；没有可靠基线时，不把播放或涨粉变化归因于 AI。

Portfolio 中可以分别体现：

- 工程作品：支持生产的工具或流程，展示可靠性、时间与质量评估。
- 创作作品：具体音频、视频或图文及本人创作贡献。
- 账号案例：内容系列、受众假设、真实反馈，以及据此作出的调整。

## 建议顺序

1. 先做范围小的 Jev / Laya 对话分流实验，形成第一份真实模型评估报告。
2. 再完成一个带检索、工具执行和权限边界的 Agent；分流实验只有在任务需要时才接入。
3. 将真实过程与结果变成社媒内容，让作品制作同时积累公开演示材料。
